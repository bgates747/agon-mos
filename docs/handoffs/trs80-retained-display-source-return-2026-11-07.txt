TRS-80 SEA-01: source-only UART0 display consultation

Bottom line: a persistent 1KiB screen packet is a good shape for the published single-buffer sender. Returning immediately to this native/remapped guest is NOT an already-supported overlap path. First establish continuous MOS IRQ/code/state/stack visibility and exclusive UART0 ownership, or restrict useful overlap to ADL host work while MOS context stays installed. No new build/run/firmware/bench or implementation selection follows from this reply. RX-005 remains stopped for Brandon review; no RX-005 prototype is distributed.

2. Caller and lifetimes

One foreground producer, actual ADL1/MB0/IRQs enabled, normal MOS UART0 ownership. Arm a volatile done flag BEFORE submission. Set HL to a contiguous immutable packet, BC to a positive full24-bit count, DE to a non-null resident ADL assembly callback, A=25h, then RST.LIL08h. No alignment requirement or copied16-byte MOS staging buffer exists; the ISR reads your RAM source directly and writes the hardware FIFO in up-to16-byte OTIRX bursts. 1024/1920B are within the length field; allocation, physical mapping, no-wrap and lifetime still belong to the caller. The complete header/payload/RUN stream, not just screen bytes, needs one stable representation.

There is one descriptor, no queue, transfer ID, cancellation, supported overlapping submission or NULL callback. You can prepare a disjoint second packet while the first is borrowed, but cannot submit it over the first. The callback may run before the syscall returns. It is source-consumed notification: all source bytes have been copied into UART FIFO, not all bits sent or renderer work done. It runs under DI. Use the provided flag-store assembly leaf; it returns ordinary RET in the supported ADL contract. Preserve any IX/IY/alternate registers/MB touched, and do no MOS call, C runtime, output, allocation, wait or recursive submit there. Submission's AF/HL are clobbered; honor the actual host C ABI independently of ISR saves.

After callback the source may be reused. Separately observe UART TEMT for the recipe's conservative next-packet/ordinary output/exit boundary. RC3 supplies no public drain syscall; the bare-MOS example samples portC5h bit6. This read can acknowledge receive-error evidence and is not a transferable EMOS ownership interface. TEMT is not remote acceptance. A VDPlet ordered RUN/DONE reply or explicit existing fence supplies the renderer endpoint; keep module, receiver registration, token and any semantic inputs valid until that endpoint. A timeout does not cancel a borrowed source or prove a command was never executed: preserve uncertain ownership, do not free/unload/retry under a new token as though idle. Baseline/shadow advancement and dense/delta generations must distinguish submitted state from positively retired renderer state.

3. Critical source seams in THIS guest

I read apps/local-sd-bridge/read.asm and context-hooks.inc, docs/architecture/boot-chain-and-disk-driver.md, and apps/trsdos7-source/TRSDOS_7/SYSRES/interrupts/interrupt_handler.s. These source findings are not a fresh loaded-binary qualification. In particular, the current context-hooks.inc explicitly corrects an old Fab rebasing assumption; I am not reviving the older pre-remap-copy account from historical prose.

read.asm saves SPL, selects its private B7FF00 stack, selects CS0 bounds8..F/flash00, STMIX, context_swap, MOS work, context_swap, RSMIX, flashFE, then guest CS0 bounds0..7 before return. The shared context_swap exchanges16KiB at logical BC000/FC000. Ordinary MOS-call success while this mapping/context is installed does not show MOS state remains valid after the second swap or flash relocation. Moving only the screen packet to internal SRAM does not retain the MOS descriptor, callback thunk, vectors, parser globals, callback flag or long-stack memory. Those identities must all stay addressable and unmodified throughout IRQ service.

The retained guest interrupt source has a concrete additional hazard: UART0.handler/f92_UART0.handler alias STRAY.handler, which storesFF then loops forever. Its timer pump_switch path also writes screen bytes directly to UART0_THR while polling CTS/THRE. If those bindings are active in the selected guest binary, arming MOS TX IRQ without an admitted routing change will not service MOS's refill; leaving the pump enabled introduces a second UART writer. Those are source compatibility blockers, not a measured fault in your current binary. Audit the actual selected vector table, interrupt mode/base, guest DI/EI policy, pump/terminal output and keyboard RX owner, rather than assuming inherited labels prove the deployed state.

Non-ADL itself is not a blanket CPU impossibility. Tom's source contains a mixed-mode callback branch and documents RET.LIS for that case, but selects its thunk using MB, not an explicit proof of ADL. Your guest's MB0 is not proof of ADL1 or safe mixed callback entry. Our qualified consumer recipe deliberately uses an ADL1/MB0 gateway and ADL callback. RETI.L/RETI.LIL forms do not by themselves restore remapped MOS RAM or compose two interrupt owners. A direct guest-mode port would need separate verification of MADL/IM/vector entry, source address formation, SPS versus SPL, full interrupt register/upper-byte context, callback return and interrupted-mode restoration. No generic change to these is supplied by25h.

Do NOT just EI in the current DI bridge, leave MOS TX pending then swap/remap back, or hand source ownership to a stale saved16KiB context. If preserving MOS across guest execution requires substantial routing/context work, that is a separate TRS-owned design choice. The smallest first integration can instead keep the MOS-compatible ADL window intact and overlap bounded host scanning/serialization of a disjoint next screen snapshot; guest execution resumes only after source/drain/receiver requirements and mappings are retired. Guest memory access during that host work must itself use the correct physical map or a pre-copied snapshot.

4. Backpressure, receiving and renderer selection

The published RC3 sender checks CTS before each <=16-byte refill and waits inside that IRQ with DI if blocked. There is no bound on RX/keyboard/VBlank/PRT interrupt latency or stuck-receiver recovery. The private bounded-CTS/EMOS work is not installed by choosing published RC3. UART0 RX remains per-byte MOS protocol service; it is not sped up by OTIRX. A keyboard callback that changes mapping or performs transport work would violate the tiny-callback model. Preserve the selected receiver's actual callback/packet ownership and keyboard handling.

Transmit ordinary, complete VDU command bytes: async adds no required outer packet envelope and does not require VDP firmware changes for existing commands. Stock VDP can consume its existing command stream. A retained-map/native-renderer VDPlet needs the separately selected VDPlet firmware/services/module; neither RC3 nor Apple's custom F6 is that implementation. VDPlet owns those interfaces. Never interleave synchronous RST10/RST18/terminal/pump/query/mode output into a borrowed command stream; keep loader/upload/RUN reply and mode/route lifetimes serialized. Arm reply collection before sending if required by the selected protocol. New RX-005 counted receive is not part of this handoff.

5. Measurements and an appropriately small future proof

There is no universal256B threshold. Fixed syscall/IRQ/callback/check/packet-copy cost versus available overlap depends on workload and CTS. At1152000baud8N1 the ideal raw wire time is8.89ms for1024B and16.67ms for1920B, before headers/control/pauses/rendering. CHAR01's1072B stream alone is9.31ms minimum, so60Hz does not follow from a1KiB display. Compact deltas reduce wire work independently of async; compare like with like.

Retained physical Console8 PERF2 results, /Agon/mystuff/eirene-mos/docs/tasks/TM-001/hardware-perf2-r01.md: minimal Eirene OTIRX delivered106.14k payloadB/s with a checked xorshift work rate85.5% of no-traffic calibration; matched stock106.20kB/s and zero foreground work inside its blocking transfer. This is retained synthetic calculation capacity/API scheduling, not CPU-idle profiling or a guarantee for RC3/TRS. RC2's separate trimmed cohort reports86.0% and64.6% more paced work than stock in docs/tasks/RC-002/package-README.md; do not relabel those as RC3 measurements. RC3's own package qualifies functionality, not new performance. Historical clocks/receiver images and finite sample limits are part of those cohorts. Tom's Olimex percentages and emulator figures are separate evidence. I have no completed6502 application benefit result to assert here.

Future comparison, not selected execution: first prove synchronous and async with the same MOS/VDP/module, exact full/delta packet bytes, screen sequence, presentation cadence and semantic completion oracle. Hold packetization constant so batching/delta/renderer changes do not masquerade as async gain. Separate scan/change detection, packet build/copy, submit-call, callback observation, TEMT, renderer reply and whole-frame intervals. Record bytes, full/delta counts, submissions/callbacks, max outstanding=1, completed images/generations/checksum, misses/coalesced frames, keyboard/quit and errors. Match a fixed deterministic guest instruction/work quota only AFTER guest IRQ/context safety is demonstrated; before that call the overlapped work host scan/build capacity, not guest cycles gained. Normalize useful work rate by identical no-traffic calibration and retain checksums; no idle calibration means no defensible percent-compute claim. Use a genuinely free/admitted PRT, not the guest-owned timer1 driving its existing60Hz tasker. Record raw clock/rate and wrap rules; delayed VBlank IRQ service is not an independent wall clock.

Start with one complete screen packet and one positive renderer reply, exact output plus clean teardown, then full/delta sizes and guest-overlap qualification as separately chosen steps. No FPS prediction, stock compatibility extension, new owner hook or scope change is implied. This reply only supplies existing source/API constraints and a proposed future measurement design.
