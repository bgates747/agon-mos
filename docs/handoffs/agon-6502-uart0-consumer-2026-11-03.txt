Recommendation
Use borrowed writes with foreground completion events for large image uploads.
Your isolated two-buffer prefetch design is the appropriate consumer seam: keep
one immutable upload buffer owned by MOS while foreground SD I/O fills the other.
Keep the existing per-4KiB remote fences, command framing and exact-byte checks.
A 4104-byte packet fits the length limit; both buffers must lie wholly within
040000h..0BBFFFh. Start with one outstanding packet. Queueing extra packets is
optional and must not cross your existing remote fence boundary. SD work can
still block the application; this advice promises overlap, not measured savings.
Do not change the initial fd/b4 scheduler control comparison. Create a separate
consumer comparison when a compatible MOS is available. Once WOZ is resident on
ESP32, this TX change cannot accelerate guest disk accesses that stay there.

API contract
MOS getfunction (A=50h, B=13h, C=0) returns discovery function; invoke it for HL
table. Require UTX1, major1, minor>=3, table length>=69, flags bit4, and batch16
capability bitmap bit15 (bytes52..53). Do not assume these allocations in EMOS.
ADL=1, MBASE=0, 24-bit register ABI; indirect table entries are 24-bit pointers.
Byte offsets: 13 open; 31 poll drain; 34 close; 46 set batch (B=16);
54 write config (B=0 borrowed/stock RST18, C=0 foreground events,
HL=0 callback, DE=opaque context); 63 completion take; 66 borrowed write.
Borrowed write: HL=source, BC=positive length<=65535; A=status; HL=logical ID
on success. Entire source must fit [040000h,0BC000h). Statuses: 0 OK, 1 BUSY,
2 INVALID, 3 CLOSED, 4 CONTEXT. BUSY has not accepted ownership: bounded retry
in foreground, never replay an accepted uncertain payload. Opaque IDs are
24-bit, not persistent or guaranteed consecutive, with no indefinite wrap promise.
Take: A=OK, HL=ID, DE=context, B=kind (1 borrowed,2 copied); BUSY means no event.
Take frees the completed descriptor; retain each buffer until its matching event.
Three descriptors total; unconsumed completion events occupy capacity.
Drain requires queue drained plus UART TEMT. Take outstanding events before close.
Do not use an elapsed timeout as permission to free an accepted source.

Open alone does not change RST18. Default session checks CTS per byte. Explicit
batch16 selects up to16 writes per bounded FIFO refill using OTIRX, checking CTS
before each block, including descriptor boundaries, but not each byte inside it.
The 16-byte storage is the UART hardware FIFO, not a MOS payload staging buffer.
Refills respect FIFO availability, contiguous source and a16-byte service budget.
MOS owns the shared UART RX/TX ISR and retains its normal RX parser; app interrupts
must not compete for UART ownership. A blocked CTS retains source ownership.
Completion is SOURCE_CONSUMED, distinct from wire drain and from VDP execution.
Keep your remote fence/acknowledgement to establish receiver processing.

Copied RST18 is an alternative convenience, not my recommendation for large uploads:
configure B=1,C=1; HL=callback or0. Three256-byte copies consume768B fixed MOS RAM.
The original source is reusable at return; large calls can block waiting for slots.
One logical completion per call, not per chunk. C=0 copied mode is rejected.
A direct callback gets A=4,HL=ID,DE=context, interrupts disabled, potentially before
submission returns or later in UART ISR. Only post bounded flags/IDs; no API reentry,
SD, output or waiting. Preserve ADL/MBASE and leave DI. Foreground events are simpler.

Keyboard/readback sequencing — material restriction
I inspected experiments/vdp005/bulk_read/mos_app.c: it installs apple_packet_callback
before its upload. That lifetime cannot coexist with this async session.
Async open refuses a nonzero MOS user keyboard callback. Installing one drains and
closes an async session, but that implicit behavior is not a substitute for explicit
ownership sequencing. Finish all prior reverse traffic, detach only your owned hook,
open/configure/upload, collect source completions, drain, close, restore/install the
readback hook, THEN issue the reply-producing remote fence/readback request. Restoring
the hook only after issuing that request could lose early replies. Preserve the exact
previous hook and never detach in the middle of a reverse packet. Standard MOS keyboard
state remains available while the user hook is detached. This transport accelerates
TX only; it supplies no bulk RX or SD persistence improvement. No synthetic RX syscall
is needed while MOS owns the UART interrupt. Your proposed detach/drain/restore seam
fits these constraints, provided no command can elicit custom-hook-only replies while
it is detached. If upload commands themselves can do so, retain synchronous fallback
until the protocol explicitly resolves that lifetime conflict.
