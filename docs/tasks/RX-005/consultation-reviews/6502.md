# RX-005 consultation — whole-block returns for Apple disk persistence

A registered, counted receive buffer could replace our keyboard-callback mailbox
and dozens of synchronous pulls per disk block. One outstanding receive is
sufficient. Keep durable disk acknowledgement separate from receiving bytes.
This is an existing-source requirements review only; it selects no ABI,
implementation, compilation, test, reservation, deployment or resumed goal.

1. Source identity and active-product distinction. Project HEAD is
   46b5a8aeb5a3ce84f63190ce3045f5a79b525eb5; reviewed file SHA256 identities are
   in RX-005-CONSULTATION-R01.json. The ESP32-machine/eZ80-filesystem frontend
   implements saving; the separately prepared pre-sound eZ80 CPU/controller
   comparator under IO-003 is read-only. Do not describe their capabilities as
   interchangeable. CPU-003's preserved playable source is generated at
   build/cpu003/playable-r03/app/mos_app.c, with transport in app-sources/.
   Its Olimex r02 transport has identical bytes. No package was changed.
2. Our workaround uses keycode packet0x81, NOT literal key-map packet0x88.
   VDP donor src/vdplet_runtime.h sends PACKET_KEYCODE, with VDPL signature,
   protocol/kind/token and data in its body. Normal replies have10-byte bodies
   (two useful data/status bytes); READ_BYTES replies have16-byte bodies (eight
   useful data bytes). Each adds a two-byte packet envelope. Client callback
   receives borrowed DE-addressed scratch with no explicit length argument.
   bulk_read/client.c::br_receive recognizes signature/kind/token, copies into
   its own mailbox, neutralizes the signature and publishes ready last.
   packets.src chains genuine keys to the existing SDK handler. This is not a
   keyboard-map upload or a direct application receive buffer.
3. Actual serialized exchange: playable/mos_transport.c::br_copy issues one
   operation6 per1..8 requested bytes, waits for its reply, then copies the
   mailbox's data into the final destination. READ16 fallback is two bytes and
   needs a readable spare second byte for an odd tail. wait_reply spins on ready
   with tick/spin bounds. Foreground guards preserve prior interrupt state.
   The later playable client adds clean INFO0 epochs before16-bit token reuse;
   an uncertain session stays poisoned. This bookkeeping and borrowed scratch
   copying are concrete simplification targets, not arguments for retaining
   the eight-byte limit in a general receive service.
4. Useful operations/sizes. Disk EXPORT at RESULT1792 yields a40-byte descriptor;
   RESULT2048 yields up to512 payload bytes. Normal full descriptor plus block
   takes69 eight-byte pulls (5+64), or276 READ16 requests (20+256). These are
   source-derived counts, not a new speed result. Return one descriptor and one
   whole block, or a552-byte combined bounded export if the operation supplies
   that snapshot. Existing state/header/clock consumers use40/48/128/8-byte
   spans; diagnostic text snapshots use960 bytes and optional main-RAM captures
   use64KiB in4096-byte chunks. A512-byte minimum useful bulk case is ample for
   our first consumer; no16-byte application cap is justified. Full-RAM capture
   is a diagnostic convenience, not a prerequisite for the transport.
5. Rates. Disk returns are bursts when dirty data is exported, on save/eject/
   reset/exit or explicit retry; no source-required60/120Hz stream. The frozen
   SAVE oracle dirties six512-byte image blocks. Command completion/status can
   occur at each host-controlled invocation; clock reads are eight bytes.
   There is no independently calibrated sustained physical return rate to
   specify. Historical emulated results in2026-11-01-vdp005-bulk-read are not a
   new measurement or a requirement for RX-005. No incremental or fixed388ef52
   cumulative performance measurement is available for this proposed service.
6. Disk ownership stays above the generic transport. Pause/quiesce the guest,
   EXPORT a stable descriptor/payload, validate drive/image/epoch/generation/
   length, receive into eZ80 RAM, perform foreground MOS/FatFs seek/write/sync/
   close/reopen/exact readback, then ACK the exact export. Failures retain dirty
   data; receive completion never authorizes disk ACK. No filesystem or lengthy
   C work in an IRQ callback. Keep generation/image identifiers in the disk
   operation even if the generic transport does not need request IDs.
7. Minimum registration/completion contract. Admit destination and capacity
   before requesting output; publish status and actual byte count only after
   all successful writes are visible. A tiny interrupt completion flag/callback
   is enough, with filesystem/UI work in foreground; no new deferred executor
   is required. Define busy/unarmed/oversize/truncated/error outcomes, storage
   lifetime, rearm/detach and late replies. Never overwrite capacity or report
   a short transfer as a complete disk block. On oversize, do not leave the
   remaining counted payload to be parsed as legacy packets. An API specifying
   clean refusal before send or bounded drain can satisfy this; no specific ABI
   or opcode is selected here.
8. One outstanding receive suffices for our actual serialized exporter and
   control replies. A generic wire request ID is unnecessary IF ordered output,
   one producer/operation and definite completion-or-retirement prevent an old
   reply being assigned to a newly registered buffer. Timeout alone is not
   retirement. Either provide that stop/drain/cancel lifetime guarantee, or
   retain the smallest generation/token needed to reject late data. No queue,
   channels, retries, echo or CRC framework is requested. Existing callbacks
   cannot safely be detached while late private packets remain possible; this
   is why the current code uses a teardown fence/quarantine.
9. Pacing and coexistence. New typed return packets must coexist with ordinary
   keyboard/F-key/mode/point replies without repurposing the keyboard vector.
   Serialize whole packets between producers: no keyboard byte insertion into
   a counted bulk body. Registered capacity does not supply UART flow control.
   Bound peer production against actual receive service, FIFO occupancy and
   IRQ masking; do not require uninterrupted512-byte bursts merely because a
   destination is512 bytes. Our older eZ80 interpreter masks IRQs in guest
   chunks; a faster parser alone does not qualify those intervals. Separate
   this known concern and current IO-003 incomplete-MODE investigation from
   claims about any new receive design.
10. Completion stages are different: TX source release means sender no longer
    borrows the request buffer; UART drain means its final bit left the sender;
    computation completion means the requested VDP/module operation finished;
    successful receive completion means the counted result is in destination
    RAM; reply retirement means no old transfer can later target reused storage.
    Durable disk commit/ACK is an additional application stage. Do not infer
    these from a shared callback or an INFO fence without an explicit contract.
11. Proposed future matched demonstration, not selected execution: reuse our
    module-free512-byte known-pattern readback utility, compare existing eight-
    byte pulls with one registered bulk receive, verify every byte and ordinary
    key/F-key events, then use genuine DOS SAVE/sync/reopen/LOAD/LIST/RUN and the
    existing missing-file/retain/retry oracle. Keep same payload/work/runtime;
    record CPU work, full reply latency, errors and heap/stack/code costs. Include
    odd/final/capacity boundaries, unarmed/late reply/rearm and normal teardown.
    No hardware calibration or cumulative baseline number may be inferred from
    wire-byte reduction. The VDPlet owner is the confirmed shared producer;
    its current PCM/audio services also use PACKET_KEYCODE, but this review does
    not claim other applications consume those services.
