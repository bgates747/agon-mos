# Same uninvoked helper — session readiness before final observation

Proposed coordination within UART12's selected delivery correction. No current
target operation or new lease is supplied here. Extender alone completes135
cleanup and respects protected successors before any new actual turn.

1. Before the final installed-state observation, Extender sends a substantive
   PREPARE-DISPATCH message identifying the actual future context/turn, exact
   source/app/host pins, original remaining budget and expected stopped handoff.
   It immediately steers/resumes Rally through the canonical Pi-native route.
   This message intentionally carries no fresh readiness epoch or consumer grant.
2. Rally reads that message in a real active turn, verifies local pins/known
   input/argv and absence of an owned consumer, and immediately returns an actual
   CONSUMER-READY response. Server acceptance alone is insufficient. This wakes
   or restores the session before its recovery delay can consume fresh evidence.
3. Only after that response does Extender take its genuine final installed
   state observation, close its target actors and deliver the actual fresh
   handoff immediately. Preserve source availability/RX/callback provenance,
   actual token/URL, min1020 and original1800/540/420/600 bounds. No old evidence
   copied forward with a newer epoch, no extension or reinstall after expiry.
4. Rally reads/checks the actual current handoff and launches the one unchanged
   application through the reviewed foreground consumer route once. Existing
  120s epoch guard stays. Self-summary precedes the first target step; original
   toolhandle/PID/start/parent/group/boot/argv registration follows immediately
   after the launch tool returns, as Extender103 explicitly clarified. No new
   wrapper, readiness barrier or impossible before-launch handle is introduced.
5. If delivery is still stale, Rally reports zero-launch/stopped custody at once.
   Only Extender may make a narrow genuine observation if the same original
   remaining budget admits the complete consumer and restoration. Otherwise
   cleanup only. Normal uncertain-operation/no-replay rules remain.

These numbered steps describe protocol order, not mutable task identities.
Task identities remain the RX6-DEL-NN checkboxes in PLAN.md. This coordination
does not authorize a second helper invocation, altered physics/rendering, app
rebuild, extra benchmark case or new receive/firmware feature.
